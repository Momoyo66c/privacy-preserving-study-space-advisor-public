# 模块 4：推荐与前端应用

## 交付给 AI 的执行指令

你负责实现 Privacy-Preserving Study Space Advisor 的个性化推荐、LLM 解释适配器和前端 Dashboard。先完整阅读 `00_SHARED_CONTRACT.md` 和模块 3 API 规格，然后检查仓库。推荐排序必须由确定、可测试的规则完成；LLM 只能润色或解释已经确定的结果，LLM 不可用时必须使用模板解释。前端必须能通过 mock API 独立开发，并最终切换到真实后端。你不得把 LLM 密钥放入浏览器、不得向 LLM 发送原始热帧/雷达轨迹/声音数据。持续执行直到推荐单元测试、adapter 集成、响应式 Dashboard、加载/错误/降级状态和端到端演示全部通过。

## 1. 模块使命

把房间的当前状态、未来占用预测、环境舒适度和用户偏好转化为可解释的房间排序，并通过清晰的 Dashboard 帮助学生快速选择安静学习或小组讨论空间。

## 2. 负责范围

本模块负责：

- 用户偏好模型和推荐请求构建。
- 确定性房间过滤、评分、排序和理由生成。
- 作为模块 3 `RecommendationAdapter` 的正式实现。
- LLM provider 抽象、结构化输入、输出校验、超时和模板 fallback。
- Dashboard、房间列表、偏好设置、房间详情和趋势图。
- 当前状态、预测、置信度、stale/degraded 和隐私说明的呈现。
- mock API、前端测试和端到端演示脚本。

本模块不负责：

- 传感器驱动、特征工程或模型训练。
- 数据库 Schema 和历史预测算法。
- 让 LLM 决定事实、重写模型状态或生成未经验证的房间数据。
- 校园地图、预约系统、账号认证或消息推送，除非核心功能完成后作为可选扩展。

## 3. 技术基线

前端建议：

- React、TypeScript、Vite。
- 数据获取使用轻量 query/cache 层或清晰封装的 `api/` 模块。
- 图表使用一个可访问、可响应式调整的图表库。
- 测试使用 Vitest、Testing Library；关键流程使用 Playwright 或等价 E2E。

推荐服务建议：

- 使用 Python 纯逻辑包，放在 `backend/src/.../recommendation/` 或可被模块 3 adapter 导入的位置。
- LLM provider 使用接口封装，不把特定供应商调用散落在业务逻辑中。
- 所有排序函数对相同输入产生相同输出。

如果现有仓库已有前端技术栈，保持一致，但功能和验收标准不变。

## 5. 用户偏好

UI 至少支持：

- 学习模式：安静学习、讨论、任意。
- 安静优先程度。
- 低占用优先程度。
- 明亮环境优先程度。
- 温湿度舒适优先程度。
- 距离优先程度；无位置数据时隐藏或禁用，并解释原因。

所有优先程度使用 0 至 1 保存。前端可以用开关、分段选项或滑块呈现，但必须展示清楚含义，并提供合理默认值。

默认 profile：

```json
{
  "study_mode": "quiet",
  "quiet_priority": 0.8,
  "low_occupancy_priority": 0.7,
  "brightness_priority": 0.3,
  "comfort_priority": 0.4,
  "distance_priority": 0.2
}
```

不收集姓名、学号或其他身份数据。

## 6. 推荐流程

推荐必须按以下顺序执行：

1. 获取 active 候选房间。
2. 读取当前状态、数据年龄、置信度、传感器健康和 15/30 分钟预测。
3. 对无数据、stale、unknown 或严重 degraded 的房间应用过滤或惩罚。
4. 根据学习模式执行硬约束。
5. 计算各子分数和加权总分。
6. 使用确定的 tie-breaker 排序。
7. 生成结构化理由。
8. 可选调用 LLM 生成更自然的解释。
9. 验证 LLM 输出；失败时使用模板解释。

任何时候都先有确定排序，再有 LLM 文本。

## 7. 过滤规则

建议硬规则：

- `room_state=unknown` 且没有可靠近期历史：不进入主要推荐，放入“状态未知”区域。
- `is_stale=true`：默认不进入前两名，除非所有房间均 stale；此时明确警告。
- `confidence < 0.55`：降低分数并展示低置信度。
- 安静模式下 `not_recommended_noisy_or_crowded` 排除。
- 安静模式下 `discussion_allowed` 可以保留但显著降分。
- 讨论模式下 `discussion_allowed` 加分；quiet 房间仍可用但提示避免打扰。
- 未来预测为 high 时，对要求持续可用的偏好降分。

阈值必须集中配置并有测试，禁止散落魔法数字。

## 8. 评分模型

每个子分数为 0 至 100：

- `mode_match_score`
- `occupancy_score`
- `future_availability_score`
- `brightness_score`
- `comfort_score`
- `distance_score`，无位置数据时不参与权重归一化
- `freshness_confidence_factor`，作为最终乘数或惩罚

初始基础权重建议：

| 子分数 | 基础权重 |
|---|---:|
| 学习模式匹配 | 0.35 |
| 当前占用 | 0.20 |
| 未来可用性 | 0.15 |
| 光照 | 0.10 |
| 温湿度舒适 | 0.10 |
| 距离 | 0.10 |

将用户优先程度与基础权重组合后重新归一化。具体公式必须：

- 记录在代码注释和 README。
- 对缺失维度重新归一化，不把缺失当作 0 分。
- 保持 0 至 100。
- 产生可解释的子分数组成。

建议 tie-breaker 顺序：总分、数据新鲜度、模型置信度、`room_id`，确保完全确定。

## 9. 环境舒适度

第一版采用简单可解释规则：

- 光照处于配置的学习舒适范围时高分，过暗或过亮逐步降分。
- 温度和湿度相对配置的舒适区计算偏差分。
- 规则是“学习舒适度近似”，不得表述为医学或安全判断。
- 传感器缺失时对应维度不参与权重，而不是给 0 分。

具体舒适区必须集中配置，UI 可以显示当前数值和“偏冷/舒适/偏热”等非医学标签。

## 10. 结构化理由

每个推荐先生成 2 至 4 条事实理由，例如：

- 当前适合安静学习。
- 当前占用较低。
- 预计未来 30 分钟保持低占用。
- 光照符合你的偏好。
- 数据已超过 30 秒，结果可能不准确。
- 雷达传感器降级，置信度较低。

理由必须由实际字段触发。禁止出现没有数据支持的“座位很多”“离你最近”或“肯定安静”等描述。

## 11. LLM 解释

### 11.1 允许输入

- 房间显示名称和匿名 ID。
- 当前分类状态、占用等级、适合度和置信度。
- 结构化环境摘要。
- 未来占用枚举和预测可靠性。
- 用户的非身份偏好。
- 已确定的排名、分数和结构化理由。

### 11.2 禁止输入

- 完整热阵列。
- 原始雷达帧或可关联轨迹。
- 声音波形或原始录音。
- 用户姓名、学号、邮箱。
- API 密钥和内部日志。

### 11.3 输出约束

- 每个房间 1 至 2 句，简洁说明推荐或不推荐原因。
- 不改变排名、分数、状态或预测。
- 不声称精确人数，除非未来系统有经过验证的明确字段；当前只说占用等级。
- 不把低置信度结果写成确定事实。
- 输出经过长度、字段和内容校验。

### 11.4 失败和降级

出现超时、限流、密钥缺失、非法输出或 provider 故障时：

- 保留确定排序。
- 使用结构化理由拼接模板解释。
- 返回 `explanation_source=template` 和可诊断但不泄密的 warning。
- 前端不弹出阻断核心流程的错误对话框。

LLM 默认超时和重试次数应保守，避免拖慢演示。

## 12. Dashboard 信息架构

### 12.1 顶部状态

- 项目名称和简短隐私说明。
- 后端连接状态和最后更新时间。
- 全局刷新按钮或自动刷新状态。
- 系统 degraded 时的非阻断提示。

### 12.2 偏好区

- 学习模式选择。
- 优先级设置。
- “应用偏好”动作。
- 恢复默认值。
- 保存成功、验证错误和后端失败状态。

### 12.3 推荐列表

每个房间至少显示：

- 排名、名称和推荐分数。
- 当前状态和占用等级。
- 未来 15/30 分钟预测。
- 2 至 4 条理由或简短解释。
- 模型置信度。
- fresh/stale、传感器 degraded 标记。

不要把每个信息都包装成同样大小的卡片。第一名可以有清晰主视觉，其余使用紧凑列表，以减少界面噪声。

### 12.4 房间详情

- 当前状态时间线。
- 声音强度、光照、温度、湿度趋势。
- 占用等级历史和未来预测。
- 32 x 24 归一化低分辨率热图预览；必须标注“非摄像头图像，仅用于当前整体热分布，不保存历史”。预览缺失或过期时显示 unavailable，不影响其他信息。
- 数据新鲜度、模型版本、置信度和传感器健康。

### 12.5 隐私说明

页面可见位置说明：

- 无 RGB 摄像头。
- 无面部或身份识别。
- 不保存原始语音。
- 展示的是整体状态和占用等级。

## 13. 视觉和可用性要求

- 桌面演示优先，同时在常见平板宽度可用。
- 状态不能只靠颜色表达；同时使用文本或图标。
- 蓝/绿/黄/红保持与本地指示器含义一致。
- 图表有标题、单位、图例和空数据状态。
- stale 和 low-confidence 不能隐藏在 tooltip 中。
- 所有交互可用键盘操作，表单有标签，文字对比度合理。
- 加载时使用稳定骨架/占位，避免页面大幅跳动。
- 错误提供下一步，例如重试、检查后端或等待新数据。

## 14. API 与 mock

- TypeScript 类型与共享契约一致；禁止在组件中直接使用未验证的 `any`。
- 所有 API 调用集中在 `src/api/`。
- 提供 mock server 或固定 fixture，使前端无需后端即可展示完整场景。
- mock 至少覆盖 fresh、stale、unknown、degraded、LLM fallback 和空房间列表。
- mock 还应覆盖热图正常、过期和 unavailable；热图数据不得进入推荐或 LLM 请求。
- 环境变量配置 API base URL，不写死 localhost 端口。

## 15. 刷新和状态管理

- 当前状态可每 5 至 15 秒轮询，间隔可配置。
- 页面失焦时可降低刷新频率。
- 偏好提交后重新请求推荐。
- 保留上一次成功数据，同时展示连接失败，避免瞬间清空界面。
- 响应乱序时只接受更新的结果。
- 组件卸载时取消请求或忽略结果。

## 16. 测试要求

### 推荐单元测试

- 三个及以上候选房间在不同学习模式下的确定排名。
- 用户优先级变化引起预期排名变化。
- 缺失位置/环境维度时正确重新归一化。
- stale、unknown、低置信度和 degraded 惩罚。
- tie-breaker 稳定。
- 所有分数保持 0 至 100。
- 每条理由都有对应事实。

### LLM 测试

- provider 正常、超时、异常、非法 JSON、过长文本和事实冲突。
- 禁止字段不会进入 provider 请求。
- provider 不可用时模板解释完整且排序不变。
- LLM 返回的新排名或新事实被拒绝。

### 前端组件测试

- 推荐列表、偏好表单、空数据、加载、错误和 degraded 状态。
- 状态颜色同时有文本。
- 趋势图缺失数据时不崩溃。
- API 负载与 TypeScript 类型一致。

### E2E 测试

- 打开 Dashboard，加载三个房间。
- 修改 quiet/discussion 偏好，排名发生可解释变化。
- 进入房间详情，看到历史和预测。
- 模拟 LLM 失败，仍显示模板解释。
- 模拟后端断开，显示错误并保留上一次成功数据。

## 17. 演示脚本

准备一个 3 至 5 分钟流程：

1. 展示隐私说明和三个房间当前状态。
2. 选择“安静学习”，解释第一名的当前和未来依据。
3. 切换到“讨论”，展示排名变化。
4. 打开房间详情和趋势图。
5. 展示模型置信度和传感器 degraded 提示。
6. 关闭 LLM 或使用 fallback 开关，证明推荐仍工作。
7. 对照本地 LED/micro:bit 指示状态。

## 18. 验收标准

- [ ] 推荐排序由确定规则产生，LLM 不参与排序。
- [ ] 用户偏好会以可测试方式改变权重和排名。
- [ ] stale、unknown、低置信度和 degraded 清晰可见。
- [ ] LLM 请求不包含原始传感器或身份数据，密钥只在服务端。
- [ ] LLM 失败时模板解释可用，核心流程不中断。
- [ ] Dashboard 展示当前状态、推荐、趋势、预测、置信度和隐私说明。
- [ ] mock API 可独立演示所有重要状态。
- [ ] 前端类型与共享 API 一致，无散落的未验证 `any`。
- [ ] 组件、推荐、LLM 和 E2E 测试通过。
- [ ] README 包含安装、环境变量、mock/真实后端运行、构建和测试命令。
